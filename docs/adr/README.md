# Архитектурные решения NXKeys

ADR фиксируют причины решений, которые сложно восстановить только по коду. Они не заменяют текущую архитектурную документацию и не должны использоваться для описания ещё не реализованных идей как фактов.

## Статусы

- `Accepted` — решение действует;
- `Superseded` — заменено более новым ADR;
- `Deprecated` — сохраняется для совместимости, но не рекомендуется;
- `Proposed` — обсуждается и не является контрактом.

## Шаблон

```markdown
# ADR-NNNN: Название

- Status: Proposed
- Date: YYYY-MM-DD

## Context

Какая проблема требует решения и какие ограничения подтверждены.

## Decision

Что принято.

## Consequences

Положительные последствия, издержки и ограничения.

## Alternatives considered

Рассмотренные варианты и причины отказа.

## Verification

Какими тестами, validators или runtime evidence проверяется решение.
```

## Правила

1. Один ADR описывает одно решение.
2. Используйте точные пути и contracts из кода.
3. Неподтверждённые будущие изменения получают статус `Proposed`.
4. При замене старого решения обновите статус и добавьте ссылку на новый ADR.
5. Изменение profile schema, IPC schema, deployment boundary или execution guarantee обычно требует ADR.
