# Проверка NX Open API на рабочей станции

NX Open-документация и сборки зависят от maintenance release, установленных модулей и лицензий. Перед производственным запуском:

1. Соберите проект против `NXOpen.dll` и `NXOpen.UF.dll` установленной NX 2512.
2. Откройте тестовую деталь.
3. Запустите `Диагностика NX Open API`.
4. Сравните отчет с `config/nx2512-api-map.json`.
5. Добавьте альтернативные имена методов, если локальный API отличается.
6. Запишите журналы NX для ручных операций:
   - создание листа из шаблона;
   - создание базового и проекционного вида;
   - создание разреза;
   - наследование PMI;
   - размещение Flat Pattern View с PMI;
   - создание Parts List;
   - экспорт PDF и DXF.
7. Сопоставьте фактические builder-свойства с алиасами Runtime.

## Минимальный приемочный комплект

```text
01_block.prt
02_shaft.prt
03_housing.prt
04_sheet_metal.prt
05_small_assembly.prt
06_large_assembly.prt
```

Для каждого файла проверяются первый запуск, повторный запуск, изменение модели, потеря PMI-связи, смена формата, смена шаблона и откат ошибки.

## Почему используется reflection adapter

Публичная логика профиля стабильна, а детали NX Open могут различаться. Reflection adapter:

- компилируется против базовых NXOpen-типов;
- пробует несколько имен builders и свойств;
- не скрывает ошибки;
- записывает неподдержанные операции в отчет;
- позволяет обновлять карту без изменения Core.

Для критичного корпоративного внедрения после инвентаризации рекомендуется заменить подтвержденные reflection-вызовы на строго типизированные вызовы конкретной NX 2512 maintenance release.
