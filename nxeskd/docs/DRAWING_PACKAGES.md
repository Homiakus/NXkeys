# Комплекты чертежей

## 1. Назначение

Один `DrawingPlan` описывает один документ NX с одним или несколькими листами. `DrawingPackagePlan` добавляет уровень комплекта, в котором разные детали, подсборки и сборочный чертёж являются отдельными документами и отдельными `.prt`.

Пример структуры:

```text
Комплект изделия
├── HP.01.04.001 — Деталь
├── HP.01.04.002 — Деталь
├── HP.01.04.010СБ — Подсборка
└── HP.01.04.000СБ — Сборочный чертёж
```

## 2. Манифест

Базовый пример расположен в `config/drawing-package.example.json`.

```json
{
  "packageId": "PRODUCT-001",
  "name": "Комплект изделия",
  "revision": "A",
  "outputDirectory": "../out/PRODUCT-001-A",
  "publication": {
    "dryRun": true,
    "stopOnFailure": true,
    "resumeFromJournal": true,
    "atomicPublish": true,
    "requireAllDocuments": true
  },
  "documents": [
    {
      "documentId": "PART-001",
      "sourcePart": "../parts/part-001.prt",
      "profilePath": "part-profile.json",
      "designation": "A.001",
      "name": "Деталь",
      "documentKind": "part_drawing",
      "nativeOutput": "A.001.prt",
      "dependencies": []
    },
    {
      "documentId": "ASSEMBLY-000",
      "sourcePart": "../parts/assembly.prt",
      "profilePath": "assembly-profile.json",
      "designation": "A.000СБ",
      "name": "Сборочная единица",
      "documentKind": "assembly_drawing",
      "nativeOutput": "A.000СБ.prt",
      "dependencies": ["PART-001"]
    }
  ]
}
```

Относительные пути разрешаются относительно каталога манифеста. Относительный `nativeOutput` разрешается относительно `outputDirectory`.

## 3. Проверки планировщика

`DrawingPackagePlanner` блокирует комплект при следующих нарушениях:

- пустой список документов;
- повторяющийся `documentId`;
- повторяющееся обозначение;
- повторяющийся выходной путь;
- недопустимые символы обозначения для имени файла;
- отсутствующий source `.prt`;
- отсутствующий профиль документа;
- зависимость от отсутствующего или выключенного документа;
- зависимость документа от самого себя;
- цикл зависимостей;
- выходной файл вне `outputDirectory` при `atomicPublish=true`;
- нативный файл без расширения `.prt`.

Проверка и Preview:

```powershell
dotnet run --project .\tools\NxEskd.PackagePlanner\NxEskd.PackagePlanner.csproj -- `
  .\config\drawing-package.example.json
```

CLI выводит JSON с диагностикой и порядком выполнения. Код возврата `0` означает корректный план, `2` — блокирующую диагностику.

## 4. Порядок выполнения

Порядок вычисляется топологической сортировкой. Документ никогда не запускается раньше своих зависимостей.

```text
чертежи деталей
      ↓
чертежи подсборок
      ↓
сборочный чертёж
      ↓
проверка полного комплекта
      ↓
публикация
```

Порядок входных элементов JSON не используется как доказательство корректного порядка.

## 5. Staging и публикация

При `atomicPublish=true` исполнитель получает путь внутри:

```text
<outputDirectory>/.staging/<packageId>/...
```

До завершения всех обязательных документов итоговые файлы в `outputDirectory` не заменяются.

После успешной подготовки:

1. проверяется наличие непустого staging-файла каждого документа;
2. существующие опубликованные файлы перемещаются во временный backup;
3. staging-файлы перемещаются на окончательные пути;
4. при ошибке новые файлы удаляются, предыдущие восстанавливаются;
5. staging и backup очищаются после успешного завершения.

Это файловая транзакция. Она не является общей Undo-транзакцией Siemens NX между несколькими WorkPart.

## 6. Журнал и возобновление

После каждого документа атомарно сохраняется journal. Он содержит:

- `packageId`;
- статус документа;
- путь staging/output;
- сообщение;
- время обновления;
- флаги завершения и публикации.

При `resumeFromJournal=true` документ пропускается только если:

- journal относится к тому же `packageId`;
- его статус `Succeeded`;
- ранее подготовленный файл существует и не пуст.

Один только статус JSON без файла не считается успешным результатом.

## 7. Контракт NX-исполнителя

Core использует интерфейс:

```csharp
public interface IDrawingPackageDocumentExecutor
{
    Task<PackageDocumentExecutionResult> ExecuteAsync(
        DrawingPackageDocumentPlan document,
        string nativeOutputPath,
        CancellationToken cancellationToken = default);
}
```

Станционный NX-адаптер должен для каждого документа:

1. открыть независимую копию `sourcePart`;
2. убедиться, что она стала WorkPart и DisplayPart согласно политике;
3. сформировать профиль/overlay с нужными обозначением, видом документа и `nativeOutputPath`;
4. выполнить Inventory → Preview → Generate/Update → Validate;
5. сохранить непустой `.prt` в переданный staging path;
6. закрыть документ без изменения исходного source-файла;
7. вернуть ошибку при любом ManualReview, который политика комплекта считает блокирующим.

## 8. Что уже реализовано

- модель данных комплекта;
- строгие логические проверки;
- DAG и топологический порядок;
- CLI Preview;
- Core executor;
- dry-run;
- journal;
- resume;
- staging;
- запрет частичной публикации;
- файловый backup/rollback;
- xUnit-тесты успешного выполнения, сбоя и возобновления.

## 9. Что требует NX station implementation

- открытие и закрытие нескольких WorkPart;
- создание безопасных рабочих копий source `.prt`;
- применение overlay к профилю каждого документа;
- вызов NX-команд из пакетного адаптера;
- сбор NX syslog и inventory для каждого документа;
- проверка памяти и Builder lifecycle на длинном комплекте;
- поведение Teamcenter-managed parts;
- восстановление после аварии самого процесса NX.

До реализации и прохождения этих сценариев нельзя утверждать, что пакетная генерация нескольких NX-файлов готова к промышленной эксплуатации.

## 10. Обязательные тесты NX

Минимальный пакетный fixture должен включать:

- две детали;
- одну подсборку;
- одну верхнеуровневую сборку;
- один sheet-metal документ с DXF;
- один документ с PMI;
- один намеренно повреждённый профиль.

Проверяются:

- порядок обработки;
- отсутствие изменения source-файлов;
- отсутствие публикации при сбое последнего документа;
- возобновление без повторной обработки уже подтверждённых staging-файлов;
- восстановление предыдущего опубликованного комплекта при ошибке публикации;
- уникальность обозначений и файлов;
- повторный запуск без дубликатов managed objects.
